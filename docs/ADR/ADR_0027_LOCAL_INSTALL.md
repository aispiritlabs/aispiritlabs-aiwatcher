# ADR_0027: A local install is one binary, one database and one token

- **Status**: accepted
- **Date**: 2026-09-09

## Context

Everything this repository builds assumes a cluster somewhere in the middle
distance. The log is Laser behind a broker, the workflow store is PostgreSQL,
the object store is RustFS, identity is authentik, and each of those has a
`just` recipe that starts a container. That is the right shape for a
deployment and it is the wrong shape for the first hour: somebody who wants to
watch their own agent has to read a justfile, start two or three services and
learn which of `AIWATCHER_BUS`, `AIWATCHER_WORKFLOW_STORE` and
`AIWATCHER_PROMPT_STORE` decides what.

The defaults are already good — `wal`, `file`, `file` — so a bare `cargo run`
does work. What was missing is that nothing *says* so, and there is no way to
talk to the result except `curl`. The panel is the only client; a person at a
terminal has a hundred and twelve routes and no verbs.

Three further things were true and pulled in the same direction. A local
instance runs `AIWATCHER_AUTH_MODE=none`, so anything that can reach the port
is an admin. The `file` workflow store rewrites whole files — the outbox on
every publish, the claim table on every claim — which section 43.34 already
measured at 458 ms over fifty thousand rows. And a managed run's history, which
is the one thing the event log does not carry, is a directory of JSON that
nothing can ask a question of.

## Decision

**One binary with a command line.** `aiwatcher` grows verbs: `up` runs the
local stack, `runs`, `spans`, `prompts`, `executions` and the rest read and
write over the same REST API the panel uses, `token` and `profile` decide what
a command presents and where it goes, and `api` reaches every route that has no
verb. The shape is Obsidian's own CLI — `key=value`, anywhere on the line,
`format=json` for a script — rather than a flag parser, because the audience is
a person first.

Nothing here is a second implementation of anything: a read is an HTTP call
against a route that already exists, so a command cannot disagree with the
panel about what a run is. That also makes the remote case free — `profile set
name=prod url=… token=…` and the same verbs reach a deployment.

**A bare `aiwatcher` still starts the server.** Every other CLI would print
help. This one may not: the container image's `ENTRYPOINT` is this binary with
no arguments, and a deployment that has been running for months must not begin
printing usage text on an upgrade. `aiwatcher help` is the help.

**A fourth authentication mode, `local`.** One token, generated by `aiwatcher
token create`, held in a file only its owner can read, and read by both halves —
the CLI presents it and the server accepts it, so there is one copy on the
machine and rotating it is one write. It authenticates as an **admin**, and
that rests on a stated condition rather than an assumption: `LocalAuth::
check_reachable` says whether the listen address is the loopback interface.

**A fourth workflow store, `duckdb`,** behind a cargo feature, in the shape
`laser` has in `aiwatcher-bus` and `postgres` in this crate. It holds one
process, as `file` does and for the same reason; unlike `file` it rewrites
nothing, and it is a database `aiwatcher sql` opens read-only *while the server
is running*.

The rules stay in Rust. `prunable`, `AttemptRow::is_claimable`,
`ClaimFilter::matches` and `SlotRecord::is_available` decide, and the adapter
loads rows and asks them; the tables keep whole rows as JSON and lift out only
what is indexed or ordered by. It passes the same twenty-nine properties the
other three do, and — because DuckDB is embedded — it passes them with nothing
running.

## Alternatives considered

**A generated CLI, from `contracts/openapi.json`.** Literal parity with every
route, and it cannot drift. It lost because the commands would be named after
operation ids: `listRuns_1` is not what somebody types, and a CLI whose verbs
are generated is a CLI with no verbs. What was kept from it is the half that
was actually load-bearing — `crates/aiwatcher-cli/tests/contract.rs` checks
every hand-written path *and every query parameter* against the contract, so a
route renamed on the Rust side fails in the same commit. That test found three
verbs sending `after=` and `limit=` to routes that declare neither, which the
API would have answered with a 400.

**Widening `AIWATCHER_AUTH_INGEST_TOKENS` to cover the local case.** No new
mode, no new concept. It lost to the guardrail that is already written down: an
ingest token is at most an `Editor`, because it is a shared secret sitting in
an agent's environment. That reasoning is about *where the secret lives*, and
it does not describe a token the person at the keyboard generated on their own
machine — but the way to say so is a mode with its own name and its own
recorded reason, not a quiet exception inside the one whose whole point is that
it has none.

**Making the local token an `Editor` after all.** Rejected on a sharper point
than convenience. A single-user install runs unauthenticated *today*, where
`Credential::Anonymous` may claim any queue; a mode that added a token and took
claiming away would mean adopting the credential silently broke that machine's
own workers. `Credential::Local` is therefore its own variant, unrestricted in
`may_claim`, rather than a reuse of `Credential::Token` — the two answer that
question differently, and flattening them would have decided it by accident.

**DuckDB as a second query engine, or as the read model's store.** Not decided
here. Decision 15 of the architecture settled that a transform stays Flow DSL
text and that DuckDB from a console is not made cheaper by it; that still
holds, and this ADR does not touch it. The read model remains the in-memory
fold under `AIWATCHER_MAX_SPANS_TOTAL`. What is in DuckDB is the workflow
store — the one thing the log does not carry — and nothing that the log's own
folds already answer, which would be the second read path ADR_0026 rules out.

**Bundling an Iggy server.** Wanted, and refused for a fact about the world
rather than a preference: Apache publishes the broker as a container image and,
for Linux only, as a release binary; there is no macOS build, it is not on
crates.io, and there is no Homebrew formula. The remaining ways to have one
without Docker are to compile somebody else's server as a side effect of `up`,
which is a surprise rather than a convenience. So `up log=iggy` starts the
container when Docker is there and, when it is not, says exactly that and names
the built-in write-ahead log — which is a real durable single-node log, not a
fallback with an asterisk.

## Consequences

The local default needs nothing running and is durable: `aiwatcher up` starts
the server on the write-ahead log, generates the token if there is none, and
starts the query service when this checkout has one. Iggy and the Flow service
are children of that process and stop with it; a broker container somebody else
started is left alone.

`aiwatcher-cli` is a new crate at the bottom of the layering, and the
`aiwatcher` binary target moved into it. `aiwatcher-server` keeps
`aiwatcher-openapi`, which is a build tool with no command line to be part of.

The `duckdb` feature costs a C++ toolchain and about two and a half minutes of
first build — measured, on an M-series laptop — and pulls Arrow. That is why it
is off by default, exactly as `laser` and `postgres` are, and why `just check`
does not build it. `just test-duckdb` does, and unlike `just test-postgres` it
needs no container.

What this rules out: two processes on the local store. `duckdb` and `file` both
hold one, so a managed run that needs a separate worker is refused by name at
admission. That is the same answer as before this ADR, said by a second
adapter.

**What would make this wrong.** Three observations, each with a different
answer. If somebody's local workflow store grows past what loading live rows
into Rust can filter in a claim — the tell is `claim_attempt` latency rising
with a backlog rather than with concurrency — the predicate moves into SQL and
the "rules stay in Rust" paragraph is what has to be re-argued. If Apache
starts publishing a macOS server binary, the Iggy paragraph is wrong and `up
log=iggy` should install rather than explain. And if the CLI's hand-written
verbs ever fall behind the API by enough that people reach for `aiwatcher api`
routinely, the generated alternative was the right one and this decision should
be reversed rather than patched — the contract test is the instrument that
would show it, because it fails on drift rather than reporting it.
